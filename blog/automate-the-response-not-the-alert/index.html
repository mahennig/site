Automate the response, not the alert.

27 Nov 2026 7 min read

My last article ended with one line I want to unpack: automate the response, not only the alert. Most security automation I see is a very efficient way to create a ticket. The scanner finds something in four seconds, the ticket waits four weeks, and everyone agrees the pipeline is “shift-left”.

If an attacker gets from disclosure to working exploit in a day, your alert latency is not the problem. Your response latency is. This post is about the boring part in between: what actually happens after the red badge appears.

The gap nobody measures

Teams track mean time to detect because the tools report it for free. Few track the time from “we know” to “it is fixed in production”. That number lives in Slack threads, change advisory boards and someone’s vacation calendar.

Split the response into three steps and time each one: decide (is this real and does it affect us?), change (write the fix or the mitigation) and ship (get it through the pipeline). In my experience the change is the shortest step. Deciding and shipping eat the days. Automation should attack those two.

Pattern 1: a leaked secret gets revoked, not reported

A secret scanner that sends an email is a notification service. The useful version revokes the credential first and asks questions afterwards. Revoking a working key is annoying. An attacker with that key is worse.

This only works if rotation is a machine operation. If replacing a database password means a human edits four config files and restarts three services, you do not have rotation. You have a ceremony. The architecture decisions that make automatic revocation possible:

  • Short-lived credentials by default. CI pipelines get cloud access via OIDC federation instead of stored keys. A token that expires in an hour is a leak you can mostly ignore.
  • One secret store, read at runtime. Services fetch credentials instead of baking them into images. Rotation then means: write the new value, revoke the old one, done.
  • Every credential has an owner and a revoke path. If nobody knows how to revoke it, assume it lives forever. The LiteLLM incident from October started with an admin key that was known to be leaked and never revoked.

Pattern 2: a patch gets merged, not triaged

Dependabot and Renovate open pull requests. Humans then ignore them, because there are forty and they all look the same. The fix is not more discipline. The fix is to let the boring ones merge themselves.

name: dependabot-automerge
on: pull_request
permissions:
  contents: write
  pull-requests: write
jobs:
  automerge:
    if: github.event.pull_request.user.login == 'dependabot[bot]'
    runs-on: ubuntu-latest
    steps:
      - id: meta
        uses: dependabot/fetch-metadata@v2   # pin to a commit SHA in real life
      - if: steps.meta.outputs.update-type == 'version-update:semver-patch'
        run: gh pr merge --auto --squash "$PR_URL"
        env:
          PR_URL: ${{ github.event.pull_request.html_url }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

--auto means GitHub merges only after the required checks pass. That makes your test suite the security control. If your tests mock every database and HTTP call, auto-merge is a coin toss. Tests against real infrastructure in containers are what make this safe. I wrote an example repository for exactly that, for Quarkus.

For everything above patch level, prioritize by evidence, not by score. A CVSS 9.8 that nobody exploits matters less than a 7.5 on the CISA KEV catalog. EPSS adds a probability of exploitation. Both are free and machine-readable, so the routing rule can be code: in KEV or high EPSS means page someone, everything else waits for the next batch.

Pattern 3: a mitigation is a switch, not a project

Many critical CVEs come with a workaround: disable a feature, set a flag, block a path. http2 off; in nginx. -XX:-UseBASE64Intrinsics for the JVM. These are one-line changes that take days, because nobody pre-agreed who may make them.

Decide in peacetime. For each internet-facing component, list the switches you can flip without a full release: config flags, feature toggles, WAF rules, a route you can turn off. Make them deployable through the same pipeline, and pre-approve them as standard changes. When the advisory lands, the decision is “flip it or not”, not “schedule a meeting about the meeting”.

A switch nobody has tested is a hope. Flip each one in staging once a quarter.

Pattern 4: “are we affected?” is a query, not a thread

The first question after every big disclosure is whether you run the thing. The usual answer is a Slack thread with fourteen people grepping repositories. Generate an SBOM for every build (CycloneDX or SPDX), store it next to the artifact, and the question becomes a query:

jq -r --arg n brotli '
  .metadata.component.name as $svc
  | .components[]? | select(.name == $n)
  | "\($svc)  \(.version)"' sboms/*.cdx.json

This also exposes the trap from October: bundled dependencies. Node ships its own Brotli, and your scanner reads package.json. An SBOM generated from the built artifact, not the manifest, catches more of that. Not all of it. Runtimes and base images need their own entries.

Don’t let the bot become the breach

Every automation in this post holds power: it merges code, rotates secrets, changes production config. That makes it a target. The October LiteLLM compromise ran through a token taken from an internal agent platform, and that token could override branch protection. Automation with broad rights is just a privileged account that never takes a holiday.

  • Narrow identities. The auto-merge bot can merge. It cannot change branch protection, add secrets or approve its own changes.
  • Pin what you run. Third-party actions by commit SHA, not by tag. Tags move.
  • Log every action with a reason. “Revoked key X because scanner Y matched commit Z” is an audit trail. “Done” is not.
  • Rate limits and a big red button. A buggy rotation job that revokes everything at 3 am is an outage you scheduled yourself.
  • Humans for the irreversible. Deleting data, failing over regions, rotating root keys. Automate the preparation, keep the final click.

Where to start on Monday

Do not build a platform. Pick the credential you would least like to see on Pastebin and answer one question: can a script revoke and replace it in five minutes, without breaking production? If yes, wire the scanner to that script. If no, you just found your next architecture task.

Then turn on auto-merge for patch updates in one repository with decent tests, and watch it for a month. Most teams find the scary part was never the merge. It was admitting that nobody read those pull requests anyway.

This is my opinion, built on what I have seen work and fail. Counter-arguments are welcome at mail@markushennig.com.
